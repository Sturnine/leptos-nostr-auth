# leptos-nostr-auth

## Project management

CCPM PRDs, epics and tasks in `.claude/` stay local. Never sync them to GitHub: no epic sync, no
`gh issue` create, comment or close for ccpm work, and `github:` frontmatter stays empty. Rollouts
close tasks by updating the local files. The repo is public and these files describe unfixed bugs.

## Releases

`main` is the only long-lived branch. Changes land through PRs into `main`, which the ruleset gates on the CI checks and merge commits only.

The ruleset requires a PR branch to be up to date with `main`. Actions run only if pinned to a full commit SHA and listed in the repo's allowed actions (Settings, Actions), which must include every action a new action calls. Release tags `v*` cannot be moved or deleted, and releases are immutable once published.

Every push to `main` runs the `Release` workflow. A push that does not release runs its `release-pr` job on the tip of `main`, which runs `scripts/prepare-release.sh`: when commits since the last tag touch what the crate ships (`src`, `Cargo.toml`, `README.md`, `LICENSE`) and git-cliff (`cliff.toml`) puts one in a changelog group, it derives the version from Conventional Commits with Cargo's 0.x rules, bumps `Cargo.toml` and every lockfile, inserts the changelog section, and force-updates the `release-pr` branch and its PR. Never push to that branch or update it from `main`; pushes to `main` regenerate it, except while a release is untagged, when only a manual run does. A ruleset lets only that App (`sturnine-release-app`) write the branch, and it needs the Workflows permission. CI fails any other PR that changes the `Cargo.toml` version, and a release PR that is not the generated commit on the current `main`, and runs cargo-semver-checks against crates.io on it.

The push that merges the release PR changes the `Cargo.toml` version and runs `publish` instead; `check` fails a version change merged from any other PR. `publish` publishes that commit through trusted publishing in the `release` environment, which deploys only from `main`, and `github-release` then creates the `vX.Y.Z` tag and GitHub release on it with the changelog section as notes. Until that tag exists, `release-pr` prepares nothing; a commit merged meanwhile is picked up by the next push to `main`. A failed or cancelled release is retried by re-running its jobs, which GitHub allows for 30 days; after that, or if GitHub refuses the tag because workflow files changed since, a version on crates.io but untagged is tagged by a person with `gh release create vX.Y.Z --target <merge commit> --notes-file <its section>`.

`Release` can be run by hand with a version above the current one and at least the derived one; the release PR keeps it until the next push to `main`, which regenerates it, or while a release is untagged leaves it stale, so run it again. Run that way while a release is untagged and not on crates.io, such as one that needs a code fix, it supersedes that version: the new section takes over its entries. Run it only after that version's run has finished. While the superseding release PR is open the superseded version refuses to publish; close the PR to release it after all. A release refuses to publish if crates.io has a version above the last tag, or if the changelog lost the last tag's section; that happens only when a superseded version shipped anyway. Then, once something releasable has landed, run `Release` by hand again with a higher version: its PR skips the stuck version and restores the shipped one's section from its tag. If the shipped version has no tag yet, re-run its release first.

Agents never run the release workflows by hand, merge the release PR, push a `v*` tag, push to `main`, publish, or edit `CHANGELOG.md` entries for released versions. Commit subjects become changelog lines: write them for readers of the release notes. Listed, when they touch shipped files and are not scoped `ci`, `test`, `chore`, `style` or `build`: `feat`, `fix`, `perf`, `refactor`, `docs` and `revert` commits, any breaking commit (`chore!:`, `ci(release)!:`), a `build(deps)` that changes `Cargo.toml`, every `Revert` and `Reapply`, and a plain subject whose first word is `Fix`, `Feat`, `Docs`, `Perf` or `Refactor`. Everything else, including other types such as `security:`, is left out.
